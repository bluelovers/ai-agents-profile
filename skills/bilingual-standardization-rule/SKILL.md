# 雙語標準化規範 (Bilingual Standardization Rule)

本技能定義跨技能、跨文件與程式碼通用的**雙語（中文 zh-TW ＋ 英文 English）標準化規範**，作為各領域（程式碼註解、技術文檔、命名與標題等）的單一事實來源 (Single Source of Truth, SSoT)。

> [!WARNING]
> 各技能文案中的「中文＋英文」「中英雙語」「繁中＋英文」只標示**語言組合**，**不是規則本身**。未實際閱讀本檔即落筆，極易只輸出中英並列而違反語言順序、彈性取捨與術語錨點原則——**任何雙語產出前，必須先閱讀本規範**。

各專項技能（如 `comment-format-rules-js`、`analyze-code-commenter`、`comment-format-rules-css`、`doc-refactor-doc-optimization` 等）均以本規範為基礎，並在此之上延伸各自的領域專屬規則。

---

## 核心原則 (Core Principles)

> [!IMPORTANT]
> **最高原則 (Highest Priority Principles)**：
> 在本規範以及所有引用本規範的雙語情境中，**「彈性取捨（捨棄與保留）」** 與 **「技術術語錨點」** 為**最高原則**，任何排版、註解或文件撰寫皆需嚴格遵守：
> - **彈性取捨（捨棄與保留）**：以可讀性與資訊價值為第一考量，拒絕僵化無效的中英鏡像直譯；並且遵守彈性捨棄/保留雙語原則，當內容過長或阻礙閱讀時，應果斷彈性裁減無額外價值的語言部分。
> - **技術術語錨點**：任何情況下**嚴禁刪除技術術語原文**，核心術語必須保留英文標註作為檢索與跨語言理解的絕對錨點。

1. **中文在前，英文在後**：所有雙語對照一律以中文為首、英文接續於後。
2. **禁止假雙語**：嚴禁「英文＋英文」重複兩次的假雙語，亦嚴禁語言順序顛倒（英文在前、中文在後）。
3. **最小必要範圍**：雙語應聚焦於具備對照價值的差異單位，避免整段、整句機械式鏡像直譯。共用專有名詞僅出現一次。
4. **技術術語錨點**：不得以「在地化」或「中文意譯」為由刪除技術術語原文；首次出現時應提供標準雙語標註（最高原則，詳見上方說明）。
5. **彈性取捨（捨棄與保留）**：以可讀性與資訊價值為第一考量，拒絕僵化無效的中英鏡像直譯（最高原則，詳見上方說明）。
6. **多語言包容性**：既有內容若包含日語、韓語、德語、法語等其他語言，必須完整保留原文，並補充中文與英文雙語。

## 語言順序與排版基礎 (Language Order & Layout Basics)

### 1. 順序與分隔格式

雙語的核心是**技術術語錨點**：讓英文術語成為可搜尋、可引用的錨點，且一律**中文在前、英文在後**。補上的英文必須帶來中文所缺的**技術術語錨點**；若中文已內嵌術語錨點、或英文僅為常見詞直譯（未提供任何技術術語），該英文即屬冗餘重複，應改以單語。雙語**不是**把同一內容中英雙版本並列。

- **術語括號格式**（主力）：中文譯名在先，英文術語置於半形括號內，例如：`快取 (Cache)`、`型別守衛 (Type Guard)`。
- **短標籤斜線格式**：簡短術語標籤以斜線 `/` 分隔（前後留空格），英文即為錨點，例如：`快取鍵 / Cache Key`。
- **雙語多行格式**：較長說明若中文行為純中文（未內嵌錨點），可採「中文語意行＋英文技術術語行」分行並陳；英文行須含演算法、資料結構等技術術語錨點（而非中文的常見詞直譯）。

> 以下為排版語法示範，非主張該句應雙語；實作時仍依判定基準與彈性取捨，短句自明者單語即可。

```markdown
<!-- ✅ 正確：術語括號錨點 -->
型別守衛 (Type Guard)

<!-- ✅ 正確：短標籤斜線錨點 -->
快取命中率 / Cache Hit Rate

<!-- ✅ 正確：雙語多行（中文語意行＋英文技術術語行） -->
以二分搜尋取得排序快取中的目標索引
Get target index in sorted cache via binary search

<!-- ❌ 錯誤：中文已內嵌術語錨點，再補英文全譯鏡像（重複） -->
初始化優先佇列 (Priority Queue) 並配置快取 (Cache) 空間
Initialize Priority Queue and allocate Cache storage

<!-- ❌ 錯誤：英文僅為常見詞直譯，無技術術語錨點（重複） -->
驗證訂單資料格式與必填欄位
Validate order data format and required fields

<!-- ❌ 錯誤：假雙語（兩行皆為英文） -->
Process data
Process data

<!-- ❌ 錯誤：語言順序顛倒（英文在前、中文在後） -->
English description / 繁體中文說明
```

### 2. 雙語標題格式規範

在 Markdown 文件或章節標題中，雙語標題應合併為**單一行**，嚴禁拆分為兩個獨立標題導致產生空章節：

```markdown
<!-- ✅ 正確：單行雙語標題 -->
## 技術術語保留原則 / Preserve Technical Terms

<!-- ✅ 正確：較長英文說明以引用區塊置於內文 -->
## 技術術語保留原則

> **Preserve Technical Terms**
>
> 核心原則說明...

<!-- ❌ 錯誤：拆分為兩個同級標題產生空章節 -->
## 技術術語保留原則
## Preserve Technical Terms
```

## 彈性捨棄雙語原則 (Flexible Bilingual Omission)

當雙語造成**閱讀障礙**或**內容過長**時，保留最清晰的一種語言即可，無需強制全面雙語。

**例外**：技術術語的雙語標註仍應保留（如 `聯合型別 (Union Type)`、`快取 (Cache)`）。

### 判定基準 (Quick Check)

檢視雙語中的**英文部分**：**不懂英文、只理解簡單單字的人，是否也知道？**

- **知道**（如 `Code`、`Problem`、`text` 這類日常簡單詞）→ 英文對中文讀者未提供新資訊：屬可捨棄的雙語，二擇一保留（見「無意義雙語」）。
- **不知道**（需具備英文程度才懂，如 `Cache`、`Union Type`、`cure-poison flag`）→ 英文是理解與搜尋的關鍵入口：保留雙語。

### 判定結果對照表

| 雙語／單語 | 英文部分判定 | 結果 | 處理後型態 |
| :--- | :--- | :--- | :--- |
| `技能說明文字 / description text` | **知道**（常見簡單詞，無新資訊） | **捨棄英文** | `技能說明文字` |
| `解毒標記 / cure-poison flag` | **不知道**（領域複合詞，具理解與搜尋價值） | **保留不變** | `解毒標記 / cure-poison flag` |
| `行動後硬直`（原無英文） | **有價值／不知道**（缺英文讀者無對照錨點） | **新增雙語** | `行動後硬直 / post-action stiff` |
| `行動後硬直`（局部核心詞） | **有價值但僅需核心詞**（非慣用整句對照） | **最小新增** | `行動後硬直 (stiff)` |

### 最小必要範圍 (Minimum Necessary Scope)

**❌ 負面案例：**
```text
Krea 2 Pixel Art LoRA 使用陷阱 / Krea 2 Pixel Art LoRA Pitfalls   ← ❌ 錯誤
```
`Krea 2 Pixel Art LoRA` 在兩側完全相同，非翻譯只是重複陳述，導致整行長度翻倍。

**✅ 正確做法：**
共用專有名詞僅出現一次，僅對真正有差異的部分進行雙語處理：
```text
Krea 2 Pixel Art LoRA 使用陷阱              ← 若 Pitfalls 經判定屬無額外價值：直接單語
Krea 2 Pixel Art LoRA 使用陷阱 (Pitfalls)   ← 若需要英文對照：僅差異詞局部雙語
```

### 譯名不唯一的術語 (Variant Translations)

「譯名不唯一」有兩個方向；無論哪個方向，**嚴禁只保留帶歧義的中文譯名**。

**方向 A：1 英文 → N 中文譯名**
英文術語本身明確，但中文有多種譯法（例如 `Cache` → 快取 / 緩存 / 緩衝）。若只保留中文譯名，不同讀者以不同譯名搜尋將無法比對。

**方向 B：1 中文詞 → N 英文概念**
單一中文詞會把多個不同概念坍縮成一個（例如「萬用字元」同時涵蓋「某特定專案具名定義的值集合或語法」與「globbing metacharacter」兩種語意）。若譯為中文，讀者無法判斷指的是哪個概念。

**兩者皆必須採用以下二者之一：**
1. **必要性雙語**：`快取 (Cache)`、`解毒標記 (cure-poison flag)`（中文譯名 ＋ 英文錨點）。
2. **僅保留英文**：`Cache`（以英文為唯一標識，從根源避免譯名歧異）。

### 大小寫消歧與術語約定區塊 (Capitalization Disambiguation & Terminology Convention)

當專案具名概念與通用計算詞**共用同一英文詞**（如 `Wildcard` vs `wildcard`）時，可採用**大小寫消歧**：專案術語首字大寫、通用詞維持小寫，並以程式碼識別字的小寫形式（如 `wildcard_manager.py`）作進一步區隔。

同時建議在文件開頭建立**術語約定區塊**，宣告該詞的處理方式與理由（適用方向 B 的「1 中文詞 → N 英文概念」碰撞）：

```markdown
## 術語約定：`Wildcard` / Terminology

> [!IMPORTANT]
> 本文件**一律保留 `Wildcard` 英文原詞**（首字大寫），不譯為「萬用字元」。

| 意義 | 本文寫法 | 說明 |
| :--- | :--- | :--- |
| **本專案的 Wildcard** | `Wildcard`（首字大寫） | 某特定專案具名定義的值集合或語法，由 `__name__` 引用 |
| **一般運算的萬用字元** | `` `*` ``（以符號標記） | globbing metacharacter，用於模式比對 |

若將專案的 `Wildcard` 譯為「萬用字元」，讀者無法判斷指的是某特定專案具名定義的值集合或語法、還是 `*` 比對語意。依「譯名不唯一 → 僅保留英文」，採用僅英文並首字大寫，以便與程式碼識別字（一律小寫）及英文原文的通稱用法區隔。
```

### 層疊語意的專有名詞／品牌名 (Layered-Semantic Proper Nouns)

部分專有名詞／品牌名**刻意同時喚起多重語源**，翻譯成中文時必然只能承載其中一層，捨棄其餘語意。例如 Google 的 `Gemini`：

- 源自拉丁語「雙子」(twins)，象徵 **Google Brain 與 DeepMind 兩大團隊合併**；
- 呼應**雙子座**「快速適應、多視角觀察」的特質，對應模型的**多模態 (Multimodal)** 與通用能力；
- 致敬 **NASA「雙子星計畫」**（Project Gemini，為阿波羅登月鋪路的載人太空計畫）。

若譯為「雙子座」會誤導為占星、譯為「雙子星」又偏離品牌意圖。這類具**層疊語意**的專有名詞宜**保留英文原詞**（回到「譯名不唯一 → 僅保留英文」），否則譯名必然削減品牌刻意營造的多重語源共鳴。

### 無意義雙語（可捨棄）

同時滿足下列三個條件時，雙語屬**無意義**，只需保留一種語言：

| 條件 | 說明 |
| :--- | :--- |
| **無歧義** | 中英語意完全相同，不會因語言不同而產生不同解讀。 |
| **無技術術語** | 不含需要保留原文比對或定位的技術術語。 |
| **無搜尋比對問題** | 保留一種語言即可滿足以關鍵字搜尋與代碼比對的需求。 |

常見無意義雙語範例：
- `程式碼 / Code` → 保留單一語言
- `問題點 / Problem` → 保留單一語言
- `正確做法 / Correct fix` → 保留單一語言

### 有特殊意圖的雙語（不可捨棄）

當中英詞彙**彼此不對應**——中文不會被自然翻譯為該英文，英文亦不會被自然翻譯為該中文時，雙語為**必要保留**，以維護意圖對應與雙向檢索：

```text
增益前綴 / Up prefix   ← ✅ 必須雙語（「增益」不直譯為 Up，Up 亦不直譯為「增益」）
增益 / Gain            ← ✅ 保留雙語以利精確理解與雙向檢索
增益 / Up              ← ✅ 保留雙語
```

## 變體：彈性保留雙語 (Flexible Bilingual Retention)

「彈性保留雙語」與「彈性捨棄雙語」**一體兩面、本質相同**：都只保留真正具備雙語價值的內容，差別僅在取捨方向：

| 面向 | 彈性捨棄雙語 (Omission) | 彈性保留雙語 (Retention) |
| :--- | :--- | :--- |
| **出發點** | 已有中文＋英文 → 判斷能否刪除其一 | 內容逐段拆解 → 判斷哪些資訊單位需要雙語 |
| **判斷方向** | 由整體向下裁減 | 由局部向上組合 |
| **典型情境** | 修剪既有冗長雙語內容或註解 | 撰寫新內容，決定哪些詞彙需標註英文 |

### 四條核心規則

1. **最小必要範圍**：雙語縮小到真正需要的資訊單位，而非整句整段雙語化。
   - `使用快取 (Cache) 避免重複查詢。`（僅對術語雙語）
2. **不要求完整鏡像對照翻譯**：不需要「中文一句、英文一句」的死板翻譯，中文為主的段落自然混入必要英文即可。
   - `使用快取 (Cache) 儲存 API response，避免相同 request 被重複送出。`
3. **同句可混合單語與雙語**：中文、英文、中英對照可自然共存於同一句中。
   - `啟用 Cache 後，使用者資料先從快取取得，未命中才執行 API request。`
4. **有額外價值才雙語**：英文具備搜尋、辨識或對照價值時才保留；純直譯且無額外價值者使用單語（回到判定基準）。

### 雙語保留判定表

| 情況 | 建議處理方式 |
| :--- | :--- |
| 中文已足夠清晰表達 | 僅保留中文 |
| 英文已足夠清晰表達 | 僅保留英文 |
| 英文只是中文直譯、無額外價值 | 省略英文（經判定基準確認） |
| 中文只是英文直譯、無額外價值 | 省略中文（經判定基準確認） |
| 技術術語需保留原文 | 局部雙語標註，格式：`中文 (Term)` |
| 英文是關鍵搜尋／比對錨點 | 雙語或僅保留英文（如譯名不唯一術語） |
| 一句中僅個別名詞需英文對照 | 僅針對該名詞局部雙語 |
| 內容牽涉跨語系協作或合約定義 | 使用完整雙語對照 |
| 雙語導致內容過長影響閱讀 | **先縮小雙語範圍**（僅保留術語雙語），仍過長才捨棄次要語言 |

## 技術術語保留與標註規範 (Technical Term Preservation)

### 核心原則

**技術術語嚴禁刪除。** 嚴禁以「在地化翻譯」或「文字通順」為由，刪除原始英文術語。

### 標註格式標準

| 做法 | 格式規範 | 範例 |
| :--- | :--- | :--- |
| **一般術語標註** | 中文在前，英文術語在後加括號 | `聯合型別 (Union Type)`、`快取 (Cache)` |
| **縮寫標註** | 縮寫在前，英文全稱在後加括號 | `E2EE (End-to-End Encryption)`、`AST (Abstract Syntax Tree)` |
| **複合完整標註** | 中文 (英文全稱, 縮寫) | `大型語言模型 (Large Language Model, LLM)` |
| **情境嵌入保留** | 句子中嵌入術語並輔以原名稱 | `TypeScript 的型別守衛 (Type Guard) 能在執行期收窄型別...` |
| ❌ **錯誤做法** | 僅用中文通俗描述而刪除原文 | `此函式可處理多種可能的型別`（遺失 Union Type 原文） |

### 語言關鍵字保留英文原字 (Language Keywords Preserved in English)

部分程式語言的關鍵字與語法建構（如 `enum`）**保留英文原字**，不以中文在地化詞（`列舉`、`枚舉`）取代，以便與程式碼識別字直接比對、搜尋與引用：

| 做法 | 範例 |
| :--- | :--- |
| ✅ 保留英文關鍵字 | `enum Status`、以 `enum` 定義狀態值集合 |
| ❌ 以中文在地化詞取代 | 以「列舉」（zh-TW）／「枚舉」（zh-CN）定義狀態值集合 |

## 保留其他語言原始內容 (Preserve Other Languages)

**核心原則：若原始內容或註解包含中文與英文以外的語言，一律保留該語言。**

當遇到包含簡體中文、日語、韓語、德語、法語等其他語言時，**絕不可刪除或覆蓋**：

| 情境 | 處理方式 |
| :--- | :--- |
| **原文為純其他語言（如日語）** | 完整保留該語言內容，並在其後／下方新增中文與英文雙語翻譯。 |
| **原文為多語言混合（如日、中）** | 保留既有所有語言，維持原始結構，若缺少中英對照則補齊。 |
| **原文為中英雙語** | 遵循本規範雙語核心原則 **彈性取捨（捨棄與保留）** 與 **技術術語錨點**，判斷是否需要清理或調整。 |
| **原文為包含簡體中文** | 保留簡體中文，並在其後／下方新增英文雙語翻譯。無需額外添加/轉換為繁體中文。 |
| **原文為英文語言** | 保留該語言，並根據 **彈性取捨（捨棄與保留）** 與 **技術術語錨點** 判斷是否需要添加雙語翻譯，不需刻意額外添加/轉換為繁體中文。 |

調整/添加雙語時仍須遵守本規範的格式標準，尤其是 **彈性取捨（捨棄與保留）** 與 **技術術語錨點** 等核心原則。

```text
// ✅ 正確處理：保留原始日語並追加繁中與英文雙語
パスワードを暗号化する
密碼加密函式
Password encryption function
```

## 注意事項與邊界約束 (Critical Caveats & Constraints)

1. **嚴禁轉換原始程式碼或註解漢字**：不得擅自將檔案中既有的日文漢字、簡體中文等批次轉換為繁體中文。繁體中文僅限於**新增**或**明確要求重構**的雙語內容。
2. **禁止假雙語與倒置排版**：檢核產出，確認中文在前、英文在後，且兩者非相同英文。
3. **避免無意義的鏡像複製**：代碼註解或文檔描述中，不應逐字機械直譯導致內容臃腫，恪守「最小必要範圍」。
4. **維護雙向檢索性**：保留關鍵詞（尤其是專有名詞、錯誤代碼、設定鍵名）之中英對照，使不同語系之使用者或 Agent 均能精準搜尋。
5. **保持一致性**：在整個專案中，相同術語的翻譯應保持一致。
6. **避免過度翻譯**：僅對必要內容進行雙語翻譯，避免對所有文字進行機械翻譯。
7. **最高原則優先**：「彈性取捨（捨棄與保留）」與「技術術語錨點」為最高原則，與本節其他約束衝突時以前者為準。
8. **生產環境**: 面向生產環境的語言應保持原樣或單一性，不進行雙語翻譯，但可根據 **彈性取捨（保留）** 與 **技術術語錨點** 判斷是否需要添加「最小必要範圍」的雙語翻譯。
