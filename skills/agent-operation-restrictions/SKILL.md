# Agent 操作嚴格限制 | Agent Operation Restrictions

本技能定義 Agent 在執行任務時必須遵守的操作邊界，確保不會在未獲使用者明確授權的情況下執行具破壞性或難以復原的操作。

---

## 🚫 四大禁止類別（需明確授權才可執行）

1. **安裝/移除/變更依賴套件** — 不自行執行 `pnpm install`、`npm install` 等
2. **啟動或停止伺服器** — 不自行執行 `pnpm run dev`、`node server.js` 等
3. **git 寫入操作** — 不自行執行 `git add`、`git commit`、`git push` 等（唯讀 git 指令視需要可用）
4. **錯誤的檔案搬移方式** — 搬移檔案必須用移動指令，禁止「刪除 → 重建」
5. **略過授權** — 禁止在未經使用者明確允許的情況下，以任何直接或間接方式嘗試規避授權限制（詳見下方）
6. **大範圍修改** — 嚴禁擅自以腳本或指令執行大範圍修改行為（詳見下方）

> 詳細禁止操作與授權判斷準則 → [forbidden-operations.md](./references/forbidden-operations.md)

---

## 🚫 禁止略過授權（底線規則）

**未經使用者明確允許，禁止以任何方式（直接或間接）嘗試略過、繞過或規避前述的授權限制。**

即使某個操作表面上不屬於上述四大類別，只要其目的或效果是在未取得授權的情況下執行未授權行為，即違反此規則。包含但不限於：

- **試圖以指令組合出未授權行為** — 例如將多個看似無害的指令串接、分包或拆解，使其整體產生原本被禁止的副作用。
- **試圖寫入腳本檔案後執行可能包含未授權行為的腳本** — 例如先建立 `.sh` / `.ps1` / `.js` / `.ts` 等腳本，再以執行腳本之名義間接執行其中隱含的未授權操作。

> 凡涉及未授權的破壞性或副作用操作，無論以何種形式包裝，都必須先取得使用者明確授權。

---

## 🚫 嚴禁擅自執行大範圍修改

**嚴禁在未經使用者明確允許的情況下，擅自以腳本或指令執行大範圍修改行為。**

大範圍修改指一次影響大量檔案、目錄或跨多處程式碼的變更，例如批次重新命名、全倉庫字串替換、跨檔案自動重構腳本等。此類操作風險高、難以即時審查與復原，必須先取得使用者明確授權，並在可行時：

- 先以唯讀方式（如搜尋、預覽 diff）確認影響範圍再執行；
- 優先採用精準、可控的變更方式，避免「地毯式」掃描修改；
- 若任務確實需要大範圍變更，應先告知使用者範圍與風險，取得授權後再執行。

---

## 🚫 避免非必要行為

**請避免執行非必要行為。** 即使某項操作本身未被禁止，若與當前任務無關，仍不應執行，以免產生多餘的副作用、雜訊或資源浪費。

- **避免非必要的 git 查詢** — 雖然唯讀 git 指令（包含但不限於如 `git status`、`git log`、`git diff`）未被禁止，但請勿執行與任務無關的 git 查詢。
  - 例如：使用者要求執行一項與 git 或歷史紀錄無關的任務，卻試圖查詢 `git log` 的行為，即屬非必要。
  - **編輯 / 重構類任務是基於「檔案現有狀態」來進行的任務** — 此類任務以當前檔案內容為依據即可完成；包含但不限於 `git status`、`git log`、`git diff` 等查詢若對任務本身**沒有決定性關聯**，即不應執行。
  - **僅在具有明確需求與理由時才允許執行** — 例如：使用者要求比對狀態（修改前後差異、工作區與 HEAD 的差異）時。
- **避免非必要的依賴/指令位置查詢** — 企圖執行某指令（如 `tsx`、`tsc`）時，若該指令可直接呼叫，就不需要先進行不必要的依賴查詢或試圖查詢指令的安裝位置。
  - 例如：準備執行 `tsx` 卻先去 `which tsx` / `find node_modules` / `glob node_modules` 查詢其安裝路徑，而該路徑對完成任務並非必要。

> 原則：只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略。

---

## 🚫 禁止濫用或頻繁執行測試

**禁止濫用或頻繁執行測試。** 測試可用於驗證行為，但不應在一系列任務與動作中頻繁地一直執行測試。

- **應在完成一定程度的 work 後才執行測試** — 測試應安排在一個有意義的工作階段告一段落時執行，用以驗證整體結果。
- **不得因微小或無關變更而頻繁執行測試** — 下列情況不應觸發測試執行：
  - 只更改了極小一部分（如調整一行註解、變更變數名稱且不可能影響測試結果）；
  - 變更內容與測試涵蓋的邏輯無關；
  - 該變更在性質上不可能影響測試結果。
- **型別檢查與測試「二選一」，`test` 只在工作收尾時一次性執行** — 部分專案會在執行測試時同時進行型別檢查，透過 `pretest` hook 實作：
  ```json
  "scripts": {
    "pretest": "node --run test:tsc",
    "test": "node --run test:vitest:unit"
  }
  ```
  - **二選一** — 只需要型別檢查時，執行 `tsc` / `pretest`；需要測試驗證時，執行 `test`（`pretest` 會自動帶出 tsc，不得再自行拆解為 `test:tsc` → `test:vitest:unit` 分兩次執行）。
  - **不得緊接鏈結執行** — 一旦執行過 tsc/pretest，就不得隨即宣告「tsc passes. Now run unit tests.」後接著執行 `test`。執行過型別檢查後應繼續手邊工作，`test` 必須**等工作收尾之後**，再一次性執行。
  - **禁止同質任務間的反覆交替** — 不得形成「（型別檢查 and/or 測試）→ 後續任務 → （型別檢查 and/or 測試）」的反覆循環，此即屬下方的濫用測試行為。
    - **例外** — 後續任務若為**不同階段的非同質性任務**（已非同一工作的延續，而是嶄新的工作階段），則不受此限，可再次執行型別檢查/測試。

> 原則：測試是「驗證整體成果」的手段，而非每個微小步驟的必經程序。請累積到一定程度的工作後再統一執行測試，避免無意義地反覆觸發測試造成的資源浪費與輸出雜訊。

## ⚙️ 指令執行規則摘要

| 規則 | 說明 |
|---|---|
| ✅ 優先使用 `package.json` scripts | 有對應 script 時，一律先用它；不符合需求時才直接呼叫工具 |
| 🚫 禁止 `npx` | 改用 `package.json` scripts 或直接呼叫工具 |
| 🚫 禁止 `node_modules/.bin/` | 直接呼叫工具名稱即可 |
| 🚫 避免 `cd xxx &&` 前置 | 透過工具的 `cwd` 參數指定工作目錄 |
| 🚫 避免 `>nul` | Windows 環境可能產生無法刪除的 nul 裝置檔 |
| ⚠️ `ynpx` 是模組名稱 | 不是 yarn 專屬工具, 僅在直接呼叫失敗且必要時才使用 |
| ⚠️ `pnpm dlx` 謹慎使用 | 僅在直接呼叫失敗且必要時才使用 |
| ⚠️ 注意 `pre*` hook | 型別檢查與測試二選一：只需型別檢查跑 `tsc`/`pretest`；需要測試跑 `test`，且只在工作收尾時一次性執行 |

### TypeScript 執行優先順序
1. 直接呼叫 `tsx path/to/file.ts`
2. 失敗則改用 `ts-node path/to/file.ts`
3. 皆失敗則記錄至 `docs/ts-node-required.md` 並告知使用者
