# 避免非必要查詢行為 | Avoid Unnecessary Query Behavior

本檔案為 `forbidden-operations.md` 第 6 節「避免非必要行為」的細化與負面案例補充，聚焦於**「非必要查詢行為」**。

---

## 核心原則

**只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略，並且按照先後優先順序來進行。**

本節聚焦於「非必要查詢行為」：許多資訊（指令能否呼叫、依賴是否存在、框架 API 是否可用）在**直接呼叫現有代碼 / 工具**時就會自然顯現；若直接呼叫即可完成任務，就不需要先進行一連串前置查詢來「確證可行性」。

包含但不限於以下非必要查詢：

- **查詢執行路徑** — 如 `which tsx` / `where tsx` 查指令安裝位置。
- **查詢依賴是否存在** — 在尚未實際呼叫前，先確認某模組 / 套件是否已安裝。
- **查詢常見基本模組 / 框架的 API** — 對於語言標準庫或廣為人知的框架 API，無須額外查詢即可直接使用。

---

## 行為時機：區分「現在可以做 / 不需要做」與「完成後才需要做」

任務行為必須區分：

- **現在可以做 / 不需要做**：與達成目標直接相關、且現有代碼即可推進的動作，直接做；與目標無關或現有代碼已能完成的查詢，不做。
- **任務或階段性完成才需要做**：驗證、確認、比對等行為，留待工作告一段落後一次性執行。

**不要預先進行「尚未構成阻礙」或「非必要」的行為。** 例如：
- 不需要「習慣上想預先確認交付物可運行」——當你需要運行時，自然會從運行結果得知是否可以運行。
- 不需要在動手前先確認「依賴是否可解析」「測試要怎麼跑」「框架設定為何」——這些都會在實際呼叫 / 運行時自然顯現。

> 原則：先動手，遇阻再查；驗證留到收尾。把「預先確認」的衝動替換成「直接執行後看結果」。

---

## 負面案例（不應這樣做）

**案例核心原則：當現有代碼足以建立 / 重構 / 測試時，除非實際撰寫時遇到錯誤狀況或確實必須，否則不該嘗試進行「現有代碼本就可以完成任務」的非必要查詢行為。**

以下案例皆以此原則判斷：

### 案例 A：執行指令前先查詢安裝路徑

```bash
# ❌ 非必要查詢：準備執行 tsx 卻先查路徑
which tsx              # 非必要
tsx path/to/file.ts
```

```bash
# ✅ 正確：直接執行；僅在 command not found 時才進一步處理
tsx path/to/file.ts
```

### 案例 B：與任務無關的 git 查詢

```bash
# ❌ 非必要查詢：使用者要求執行與 git 無關的任務，卻先查 git log
git log
# ... 然後才開始做事
```

```bash
# ✅ 正確：直接進行任務；僅在具有明確需求（如比對狀態）時才執行 git 查詢
# （直接開始任務）
```

**補充**：編輯 / 重構類任務是基於「檔案現有狀態」來進行的任務，以當前檔案內容為依據即可完成；`git status` / `git log` / `git diff` 等查詢若對任務本身**沒有決定性關聯**，即不應執行。僅在具有明確需求與理由時（例如使用者要求比對狀態：修改前後差異、工作區與 HEAD 的差異）才允許執行。

### 案例 C：重構前為猜使用者意圖而查 Git

```bash
# ❌ 非必要且無意義：重構 SSoT 任務中先查 git diff / git log
git diff
git log
# 即便執行，log 也不能表示其內容與指定檔案有任何關聯，無法得出有意義訊息
```

```bash
# ✅ 正確：以當前檔案內容為事實基準，直接分析重複邏輯
# （閱讀指定檔案 → 找重複事實 → 抽離 shared core）
```

### 案例 D：建立 / 重構時先確認「依賴 / 框架 API 是否存在」

```bash
# ❌ 非必要查詢：尚未實際呼叫，就先確認依賴安裝 / 框架 API 可用
npm ls some-framework
# ... 然後才開始建立 / 重構
```

```bash
# ✅ 正確：直接呼叫現有代碼；若真的遇到「模組不存在 / API 不存在」的錯誤，
#        再根據錯誤訊息處理
# （直接建立 / 重構，遇錯再查）
```

### 案例 E：撰寫 / 重構 / 轉換為 Node.js 原生測試時，預先讀取現有框架設定值

```bash
# ❌ 非必要查詢：使用者要求以 node:test 撰寫 / 重構 / 轉換測試，
#    卻先去讀 jest.config.js 等現有框架設定值
cat jest.config.js
# ... 然後才開始撰寫原生測試
```

```bash
# ✅ 正確：直接以 node:test 撰寫 / 轉換；原生測試不需要沿用舊框架設定
# （直接動手，遇錯再處理）
```

### 案例 F：撰寫 / 轉換測試時，預先讀取現有 snapshot

```bash
# ❌ 非必要查詢：先去讀取現有 __snapshots__ 內容
cat __snapshots__/foo.test.ts.snap
# ... 然後才開始撰寫 / 轉換測試
```

```bash
# ✅ 正確：不論現有 snapshot 內容為何，都與「改用原生測試」的任務無關；
#        頂多只在任務完成後，確認執行結果時才會自然接觸到 snapshot
# （直接動手；任務完成後由運行結果確認）
```

### 案例 G：先確認「測試要怎麼跑、依賴是否可解析」或自行操作 snapshot

```bash
# ❌ 非必要查詢 / 操作：
# 1) 動手前先確認「測試要怎麼跑、依賴是否可解析」
# 2) 自行建立 / 修改 / 刪除 snapshot 檔案
```

```bash
# ✅ 正確：
# 1) 不需要先確認「測試要怎麼跑、依賴是否可解析」再動手；直接撰寫 / 轉換，
#    運行時自然會從結果得知是否可跑、依賴是否可解析。
# 2) snapshot 是測試工具的責任：測試工具會自行建立，不該由 Agent 手動操作變更。
```

### 案例 H：指令已定義於 package.json scripts 卻無法執行時，自行安裝依賴或進行一系列查詢

```bash
# ❌ 非必要查詢 / 操作：指令已定義於 package.json scripts 卻無法執行，
#    卻嘗試自行安裝缺失依賴，或先進行 which / find node_modules / glob node_modules 等一連串查詢
pnpm install missing-dep
which some-cmd
find node_modules -name some-cmd
```

```bash
# ✅ 正確：先「報告使用者」錯誤訊息與狀況；不得嘗試自行安裝缺失依賴，
#        也不得進行一系列查詢行為，等待使用者指示
# （回報錯誤，讓使用者決定）
```

### 案例 I：以 `node -e` 探針預先確認框架 API / 依賴可用性

```bash
# ❌ 非必要查詢：動手寫測試前，先用探針確認 node:test 是否支援 assert.snapshot
node -e "const {test}=require('node:test');test('probe',t=>{console.log('node',process.version);console.log('assert.snapshot:',typeof t.assert?.snapshot);});"
# ... 確認「可用」後才開始撰寫測試
```

```bash
# ✅ 正確：直接撰寫真正使用 assert.snapshot 的測試並執行；
#        若 Node 版本過舊不支援，運行當下就會報錯（snapshot is not a function），
#        再根據錯誤訊息處理（提示升級 Node 或改用替代方案）
# （直接動手，遇錯再查）
```

**補充**：此探針想得知的「框架 API 是否可用 / 依賴是否可解析」資訊，直接撰寫並執行真正的程式碼就會自然顯現，故屬「現有代碼本就可以完成任務」的非必要查詢；不應作為動手前的前置確認步驟。

---

## 正面模式（應該這樣做）

1. **先直接呼叫工具 / 現有代碼**，讓結果（成功或錯誤）自然說話。
2. **僅在遇到實際錯誤**（如 command not found、模組缺失、API 不存在）時，才進行針對該錯誤的查詢或修正。
3. **區分「必要」與「可能有用」**：與達成目標無關的查詢或預備動作，一律省略。

> 原則：只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略，並且按照先後優先順序來進行。
