# 避免非必要查詢行為 | Avoid Unnecessary Query Behavior

本檔案為 `forbidden-operations.md` 第 6 節「避免非必要行為」的細化與負面案例補充，聚焦於**「非必要查詢行為」**。

---

## 核心原則

**只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略，並且按照先後優先順序來進行。**

本節聚焦於「非必要查詢行為」：許多資訊（指令能否呼叫、依賴是否存在、框架 API 是否可用）在**直接呼叫現有代碼 / 工具**時就會自然顯現；若直接呼叫即可完成任務，就不需要先進行一連串前置查詢來「確證可行性」。

**當任務需求或使用者已明確要求「執行某指令」或「採用某種做法」時，該指令 / 做法就是既定輸入，不需再主動預先驗證。** 包含：

- **不預先查詢該指令的有效性 / 路徑 / 是否安裝** — 使用者已告知要用哪條指令，直接執行即可；能不能跑，執行結果會告訴你。
- **不預先查詢環境版本 / 依賴** — 不需先確認 Node / 工具版本、依賴是否安裝；這些會在實際執行時自然顯現。
- **不讀取與該指令 / 做法無關的檔案來自行判斷** — 使用者已明確給定指令，就不要再去讀設定檔「確認指令內容」或自行推敲其內部結構。
- **不主動預先分析外部依賴的實作 / 套件設定** — 使用者指定的做法若只涉及「如何使用」某依賴，不需先去讀其實作、編譯或發布設定。

包含但不限於以下非必要查詢：

- **查詢執行路徑** — 如 `which tsx` / `where tsx` 查指令安裝位置。
- **查詢依賴是否存在** — 在尚未實際呼叫前，先確認某模組 / 套件是否已安裝。
- **查詢常見基本模組 / 框架的 API** — 對於語言標準庫或廣為人知的框架 API，無須額外查詢即可直接使用。
- **查詢環境版本 / 依賴狀態** — 如 `node --version`、`npm ls`、檢查某套件是否安裝，以「確證環境可行」。

---

## 行為時機：區分「現在可以做 / 不需要做」與「完成後才需要做」

任務行為必須區分：

- **現在可以做 / 不需要做**：與達成目標直接相關、且現有代碼即可推進的動作，直接做；與目標無關或現有代碼已能完成的查詢，不做。
- **任務或階段性完成才需要做**：驗證、確認、比對等行為，留待工作告一段落後一次性執行。

**不要預先進行「尚未構成阻礙」或「非必要」的行為。** 例如：
- 不需要「習慣上想預先確認交付物可運行」——當你需要運行時，自然會從運行結果得知是否可以運行。
- 不需要在動手前先確認「依賴是否可解析」「測試要怎麼跑」「框架設定為何」——這些都會在實際呼叫 / 運行時自然顯現。

> 原則：先動手，遇阻再查；驗證留到收尾。把「預先確認」的衝動替換成「直接執行後看結果」。

---

## 使用者已明確指定指令 / 做法時：視為既定輸入，不預先驗證

當任務需求或使用者**已明確告知**要執行哪條指令、或要採用哪種做法時，該指令 / 做法即為**既定輸入**，Agent 的職責是照著執行，而非回頭驗證使用者的決定。判斷要點：

- **使用者給了指令 → 直接執行該指令**，不讀取設定檔（如 `package.json`）來「確認 / 自行判斷」指令內容，也不分析該指令內部實際使用的工具（如 `tsx` / `jest` / `vitest`）是否安裝。
- **使用者給了做法 → 直接依該做法執行**，不讀取與此做法無關的設定檔（如指定 nodejs 原生測試卻去讀 `jest.config.js`），也不主動查詢環境版本（如 `node --version`）或依賴狀態。
- **做法牽涉外部依賴 → 只依「已知 / 文件 API」使用**，不主動預先分析該依賴的實作、編譯方式、發布設定（`exports` / `main` / `module` / `types`）或套件設定檔。

**理由**：這些「有效性 / 路徑 / 版本 / 依賴 / 設定」資訊都會在**實際執行該指令的當下**自然顯現。成功即代表有效，失敗即有明確錯誤訊息可供被動處理；提前查詢不僅多餘，還可能因自行判斷而偏離使用者明確指定的做法。

> 使用者明確指定 = 指令 / 做法已拍板。你的任務是執行它，不是審查它。

## 負面案例（不應這樣做）

**案例核心原則：當現有代碼足以建立 / 重構 / 測試時，除非實際撰寫時遇到錯誤狀況或確實必須，否則不該嘗試進行「現有代碼本就可以完成任務」的非必要查詢行為。**

以下案例皆以此原則判斷：

### 案例 A：執行指令前先查詢安裝路徑

```bash
# ❌ 非必要查詢：準備執行 tsx 卻先查路徑
which tsx              # 非必要
tsx path/to/file.ts
```

```bash
# ✅ 正確：直接執行；僅在 command not found 時才進一步處理
tsx path/to/file.ts
```

### 案例 B：與任務無關的 git 查詢

```bash
# ❌ 非必要查詢：使用者要求執行與 git 無關的任務，卻先查 git log
git log
# ... 然後才開始做事
```

```bash
# ✅ 正確：直接進行任務；僅在具有明確需求（如比對狀態）時才執行 git 查詢
# （直接開始任務）
```

**補充**：編輯 / 重構類任務是基於「檔案現有狀態」來進行的任務，以當前檔案內容為依據即可完成；`git status` / `git log` / `git diff` 等查詢若對任務本身**沒有決定性關聯**，即不應執行。僅在具有明確需求與理由時（例如使用者要求比對狀態：修改前後差異、工作區與 HEAD 的差異）才允許執行。

### 案例 C：重構前為猜使用者意圖而查 Git

```bash
# ❌ 非必要且無意義：重構 SSoT 任務中先查 git diff / git log
git diff
git log
# 即便執行，log 也不能表示其內容與指定檔案有任何關聯，無法得出有意義訊息
```

```bash
# ✅ 正確：以當前檔案內容為事實基準，直接分析重複邏輯
# （閱讀指定檔案 → 找重複事實 → 抽離 shared core）
```

### 案例 D：建立 / 重構時先確認「依賴 / 框架 API 是否存在」

```bash
# ❌ 非必要查詢：尚未實際呼叫，就先確認依賴安裝 / 框架 API 可用
npm ls some-framework
# ... 然後才開始建立 / 重構
```

```bash
# ✅ 正確：直接呼叫現有代碼；若真的遇到「模組不存在 / API 不存在」的錯誤，
#        再根據錯誤訊息處理
# （直接建立 / 重構，遇錯再查）
```

### 案例 E：撰寫 / 重構 / 轉換為 Node.js 原生測試時，預先讀取現有框架設定值

```bash
# ❌ 非必要查詢：使用者要求以 node:test 撰寫 / 重構 / 轉換測試，
#    卻先去讀 jest.config.js 等現有框架設定值
cat jest.config.js
# ... 然後才開始撰寫原生測試
```

```bash
# ✅ 正確：直接以 node:test 撰寫 / 轉換；原生測試不需要沿用舊框架設定
# （直接動手，遇錯再處理）
```

### 案例 F：撰寫 / 轉換測試時，預先讀取現有 snapshot

```bash
# ❌ 非必要查詢：先去讀取現有 __snapshots__ 內容
cat __snapshots__/foo.test.ts.snap
# ... 然後才開始撰寫 / 轉換測試
```

```bash
# ✅ 正確：不論現有 snapshot 內容為何，都與「改用原生測試」的任務無關；
#        頂多只在任務完成後，確認執行結果時才會自然接觸到 snapshot
# （直接動手；任務完成後由運行結果確認）
```

### 案例 G：先確認「測試要怎麼跑、依賴是否可解析」或自行操作 snapshot

```bash
# ❌ 非必要查詢 / 操作：
# 1) 動手前先確認「測試要怎麼跑、依賴是否可解析」
# 2) 自行建立 / 修改 / 刪除 snapshot 檔案
```

```bash
# ✅ 正確：
# 1) 不需要先確認「測試要怎麼跑、依賴是否可解析」再動手；直接撰寫 / 轉換，
#    運行時自然會從結果得知是否可跑、依賴是否可解析。
# 2) snapshot 是測試工具的責任：測試工具會自行建立，不該由 Agent 手動操作變更。
```

### 案例 H：指令已定義於 package.json scripts 卻無法執行時，自行安裝依賴或進行一系列查詢

```bash
# ❌ 非必要查詢 / 操作：指令已定義於 package.json scripts 卻無法執行，
#    卻嘗試自行安裝缺失依賴，或先進行 which / find node_modules / glob node_modules 等一連串查詢
pnpm install missing-dep
which some-cmd
find node_modules -name some-cmd
```

```bash
# ✅ 正確：先「報告使用者」錯誤訊息與狀況；不得嘗試自行安裝缺失依賴，
#        也不得進行一系列查詢行為，等待使用者指示
# （回報錯誤，讓使用者決定）
```

### 案例 I：以 `node -e` 探針預先確認框架 API / 依賴可用性

```bash
# ❌ 非必要查詢：動手寫測試前，先用探針確認 node:test 是否支援 assert.snapshot
node -e "const {test}=require('node:test');test('probe',t=>{console.log('node',process.version);console.log('assert.snapshot:',typeof t.assert?.snapshot);});"
# ... 確認「可用」後才開始撰寫測試
```

```bash
# ✅ 正確：直接撰寫真正使用 assert.snapshot 的測試並執行；
#        若 Node 版本過舊不支援，運行當下就會報錯（snapshot is not a function），
#        再根據錯誤訊息處理（提示升級 Node 或改用替代方案）
# （直接動手，遇錯再查）
```

**補充**：此探針想得知的「框架 API 是否可用 / 依賴是否可解析」資訊，直接撰寫並執行真正的程式碼就會自然顯現，故屬「現有代碼本就可以完成任務」的非必要查詢；不應作為動手前的前置確認步驟。

### 案例 J：先用臨時指令 / 檔案試跑，確認可行後才寫入正式測試

```bash
# ❌ 非必要中繼步驟：先寫一支臨時測試 / 用臨時指令試跑，確認「可行」後才把內容搬進正式測試
# 1) 先建立 temp.test.ts 或下臨時指令驗證某段邏輯
# 2) 確認沒問題
# 3) 再把同樣內容寫進真正的測試檔並執行
```

```bash
# ✅ 正確：直接把未涵蓋的測試 / 模式寫入正式測試檔，執行測試即可；
#        無須先透過臨時指令 / 檔案「試跑確認」再併入
# （直接動手，遇錯再處理）
```

**補充**：這種「先用臨時測試試跑、確認可行後才併入」的流程會讓同一個任務產生過多步驟（建立臨時檔 → 執行 → 刪除 / 搬移 → 再執行），屬於「尚未構成阻礙」的非必要預備動作。直接寫入正式測試並執行，若出錯自然會從測試結果得知，無須額外的前置驗證。

### 案例 K：已知 API / 邏輯時，仍去查詢套件發布設定或複製其內部邏輯

```text
# ❌ 非必要查詢 / 操作：從現有代碼已知 `import { fixZero } from 'num-is-zero'`，
#    卻仍去讀 package.json 的 exports / main / module / types，或閱讀 dist 編譯產物，
#    試圖理解「該套件是以什麼方式設定 / 編譯 / 發布」；
#    或更糟：因「不清楚實作」或「未安裝」而自行把 fixZero 的邏輯複製到本專案
```

```text
# ✅ 正確：直接以已知 API 使用即可（import { fixZero } from 'num-is-zero'）；
#        這些發布設定（exports / main / module / types）與「消費方如何使用」無主動關聯，
#        不論套件以何種方式編譯發布，消費方都不需要主動查詢。
#        唯有當實際 import / 執行發生錯誤時，才被動根據錯誤訊息理解原因。
```

**補充（兩條重要判斷）**：

1. **被動觸發的行為，不需要主動提前查詢** — 套件「怎麼編譯 / 發布 / 設定」與消費方如何使用無關；只有在引用後執行出錯，才被動檢查錯誤訊息來理解原因，不該提前去讀其設定或編譯代碼。
2. **不該因不清楚或未安裝而自行複製套件邏輯** — 若該邏輯是套件**未提供可共用匯出**的內部邏輯：
   - **該套件是本專案開發的（同一倉庫 / 內部套件）** → 可抽離該邏輯，使其成為可被共用的匯出，再於消費處引用，而非複製。
   - **否則** → 應詢問使用者，或請求安裝 / 補齊該套件；不得自行把套件邏輯複製進本專案。
   - **唯一例外**：實際使用時因相容性 / 環境問題**不得已**必須複製邏輯（例如無法安裝、環境限制），才被動採取複製，但仍應先讓使用者知情。

### 案例 L：讀取 pnpm-lock.yaml 或其他 lock 檔案

```text
# ❌ 非必要查詢：為了「確認使用哪種套件管理」或「確認依賴版本」而去讀取
#    pnpm-lock.yaml / package-lock.json / yarn.lock / bun.lockb 等 lock 檔
```

```text
# ✅ 正確：從檔案名稱即可得知現有環境使用哪種套件管理
#        （pnpm-lock.yaml → pnpm；package-lock.json → npm；yarn.lock → yarn）；
#        無須開啟 / 閱讀 lock 檔內容。lock 檔幾乎從不需要被讀取閱讀。
```

**補充**：lock 檔唯一有意義的推論是「現有環境使用哪種套件管理器」，但這從檔案名稱（pnpm-lock.yaml、yarn.lock、package-lock.json…）就能直接得知，完全不需要也不該去讀取其內容。其餘資訊（解析後的依賴樹、版本 pinning）會在「直接呼叫現有工具 / 套件管理器指令」時自然顯現，故不應主動開啟 lock 檔查詢。

### 案例 M：使用者已指定執行指令，卻仍讀取設定檔判斷指令或分析其內部工具

```bash
# ❌ 非必要查詢：使用者明確要求「以 node --run test 作為執行測試指令」，
#    卻先讀 package.json 想自行判斷這條指令，或分析 node --run test 內
#    所使用的工具（tsx / jest / vitest 等）是否安裝
cat package.json
# ... 讀取 scripts，分析 test 指令展開後呼叫了什麼
which tsx
npm ls jest vitest
# ... 確認「指令應該有效」後才執行
```

```bash
# ✅ 正確：使用者已明確告知指令，直接執行；不讀取 package.json 自行判斷，
#        也不分析其內部工具是否安裝
node --run test
# 執行成功 → 指令有效；失敗 → 依當下錯誤訊息被動處理
```

**補充**：`node --run test` 的內部結構（會呼叫哪些工具）不是你的責任，也不是需要判斷的資訊——使用者既然已指定這條指令，就代表該指令的可行性由使用方保證。讀取 `package.json` 去「理解 / 核對」這條指令、或預先驗證其內部工具（`tsx` / `jest` / `vitest`）是否安裝，都屬多餘的預先查詢；有效性會在執行當下自然顯現。

### 案例 N：使用者已指定測試做法，卻仍讀取無關框架設定或查詢 Node 版本

```bash
# ❌ 非必要查詢：使用者明確要求「以 nodejs 原生測試建立測試」，
#    卻先讀取與原生測試無關的測試框架設定檔，或主動查詢目前 Node 版本
cat jest.config.js      # 與 node:test 無關
cat vitest.config.ts    # 與 node:test 無關
node --version          # 想確認「node:test 是否支援某 API」
# ... 確認後才開始建立測試
```

```bash
# ✅ 正確：直接以 nodejs 原生測試（node:test）建立測試；
#        不讀取與該做法無關的框架設定檔，不主動查詢 Node 版本
# （直接動手；API 支援與否、版本問題 → 執行測試時自然顯現）
```

**補充**：「指定 nodejs 原生測試」意味著舊框架的設定（`jest.config.js` 等）與任務無關；而 Node 版本 / API 支援與否，也會在實際執行測試時直接報錯顯現。兩者都不構成動手前的查詢理由——**做法已明確，就照做法做；環境問題留給執行結果說話**。

### 案例 O：動手前主動預先分析外部依賴的實作 / 套件設定

```text
# ❌ 非必要查詢：任務只需「使用」某外部依賴，卻先主動預先分析其實作與套件設定
# 1) 閱讀 node_modules/<pkg>/ 內部實作 / dist 編譯產物
# 2) 讀取其 package.json 的 exports / main / module / types / files
# 3) 讀取其建置設定（tsup.config / rollup.config / babel.config 等）
# 4) 查閱其版本變更、發佈方式、建置流程
# ... 「理解該依賴怎麼運作」後才開始任務
```

```text
# ✅ 正確：只依已知 / 文件記載的 API 直接使用該依賴；
#        不主動預先分析其內部實作、編譯方式或套件設定。
#        唯有實際使用（import / 呼叫 / 執行）發生錯誤時，
#        才被動依據錯誤訊息檢視必要部分
```

**補充**：外部依賴的「實作方式 / 套件設定 / 發布結構」與「消費方怎麼使用」無主動關聯——不論它是如何編譯、以什麼 entry 發布，都不影響你直接以已知 API 使用它。這類分析屬於**尚未構成阻礙**的預先查詢，只會在任務前累積多餘步驟；應直接使用，遇錯再被動處理（另見案例 K）。

## 正面模式（應該這樣做）

1. **先直接呼叫工具 / 現有代碼**，讓結果（成功或錯誤）自然說話。
2. **使用者已明確指定的指令 / 做法 → 視為既定輸入直接執行**：不讀取設定檔自行判斷指令、不分析其內部工具、不讀取無關設定檔、不查詢環境版本 / 依賴狀態。
3. **僅在遇到實際錯誤**（如 command not found、模組缺失、API 不存在、版本過舊）時，才進行針對該錯誤的查詢或修正。
4. **不主動預先分析外部依賴的實作 / 套件設定**：只依已知 / 文件 API 使用，遇錯再被動檢視。
5. **區分「必要」與「可能有用」**：與達成目標無關的查詢或預備動作，一律省略。

> 原則：只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略，並且按照先後優先順序來進行。
