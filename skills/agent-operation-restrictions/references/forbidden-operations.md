# 嚴格禁止操作清單 | Forbidden Operations

除非使用者在對話中**明確要求**，否則以下操作一律禁止。

---

## 1. 🚫 禁止自行管理依賴套件

嚴禁在未獲授權的情況下，自行安裝、移除或升級任何模組或依賴。

```bash
# ❌ 嚴禁（未獲授權）
pnpm install some-package
pnpm remove some-package
npm install
yarn add some-package
pnpm up
```

**正確做法**：若判斷需要安裝依賴，應告知使用者並**等待明確授權**後再執行。

---

## 2. 🚫 禁止自行啟動或停止伺服器

嚴禁在未獲授權的情況下，自行啟動或停止任何開發伺服器、測試伺服器或背景行程。

```bash
# ❌ 嚴禁（未獲授權）
pnpm run dev
pnpm run start
node server.js
```

**正確做法**：永遠假設伺服器已運行，無需進行前置確認行為。若發現伺服器未運行無法完成任務，應告知使用者並請其手動執行。

---

## 3. 🚫 禁止自行執行 git 寫入操作

嚴禁在未獲授權的情況下，執行任何會變更 git 狀態的指令。

```bash
# ❌ 嚴禁（未獲授權）
git add .
git commit -m "..."
git push
git checkout -b new-branch
git merge
git reset
git stash
```

**允許的唯讀 git 操作**（但仍應在有必要時才使用）：

```bash
# ✅ 唯讀，視需要使用
git status
git log
git diff
git branch
git show
```

---

## 4. ✅ 檔案搬移規範：使用移動指令，禁止刪除後重建

搬移或重新命名檔案時，**必須使用搬移指令**，嚴禁以「刪除原檔 → 建立新檔」的方式替代，以避免遺失 git 歷史紀錄。

```powershell
# ✅ 正確（PowerShell）
Move-Item -Path "old/path/file.ts" -Destination "new/path/file.ts"

# ❌ 嚴禁（會遺失 git 歷史）
Remove-Item "old/path/file.ts"
# 然後再建立 "new/path/file.ts"
```

---

## 5. 🚫 禁止略過授權（底線規則）

未經使用者明確允許，禁止以任何方式（直接或間接）嘗試略過、繞過或規避前述的授權限制。

即使某個操作表面上不屬於上述四大類別，只要其目的或效果是在未取得授權的情況下執行未授權行為，即違反此規則。包含但不限於：

- **試圖以指令組合出未授權行為** — 將多個看似無害的指令串接、分包或拆解，使其整體產生原本被禁止的副作用。
- **試圖寫入腳本檔案後執行可能包含未授權行為的腳本** — 先建立 `.sh` / `.ps1` / `.js` / `.ts` 等腳本，再以執行腳本之名義間接執行其中隱含的未授權操作。

凡涉及未授權的破壞性或副作用操作，無論以何種形式包裝，都必須先取得使用者明確授權。

---

## 6. 🚫 避免非必要行為

即使某項操作本身未被禁止，若與當前任務無關，仍不應執行，以免產生多餘的副作用、雜訊或資源浪費。

原則：只做完成任務「確實需要」的事；任何查詢或預備動作若與達成目標無關，即應省略，並且按照先後優先順序來進行。

> 詳細原則、負面案例與「非必要查詢行為」清單（執行路徑、依賴是否存在、框架 API 等）→ [avoid-unnecessary-queries.md](./avoid-unnecessary-queries.md)

---

## 7. 🚫 嚴禁擅自執行大範圍修改

嚴禁在未經使用者明確允許的情況下，擅自以腳本或指令執行大範圍修改行為。

大範圍修改指一次影響大量檔案、目錄或跨多處程式碼的變更，例如批次重新命名、全倉庫字串替換、跨檔案自動重構腳本等。此類操作風險高、難以即時審查與復原，必須先取得使用者明確授權，並在可行時：

- 先以唯讀方式（如搜尋、預覽 diff）確認影響範圍再執行；
- 優先採用精準、可控的變更方式，避免「地毯式」掃描修改；
- 若任務確實需要大範圍變更，應先告知使用者範圍與風險，取得授權後再執行。

---

## 8. 🚫 禁止濫用或頻繁執行測試

禁止濫用或頻繁執行測試。測試可用於驗證行為，但不應在一系列任務與動作中頻繁地一直執行測試。

- **應在完成一定程度的工作後才執行測試** — 測試應安排在一個有意義的工作階段告一段落時執行，用以驗證整體結果。
- **不得因微小或無關變更而頻繁執行測試** — 下列情況不應觸發測試執行：
  - 只更改了極小一部分（如調整一行註解、變更變數名稱且不可能影響測試結果）；
  - 變更內容與測試涵蓋的邏輯無關；
  - 該變更在性質上不可能影響測試結果。
- **依變更內容判斷是否需要型別檢查/測試（具體行動取決於任務內容）** — 僅修改註解的編輯任務與型別檢查或測試完全無關，根本不需要執行；沒有修改類型 → 不進行型別檢查；沒有直接或間接修改邏輯 → 不進行測試；兩者皆無 → 皆不需要執行。若任務確實需要驗證，只需在工作收尾時執行一次測試，用以檢查是否有編輯錯誤。
- **型別檢查與測試「二選一」，`test` 只在工作收尾時一次性執行** — 若專案以 `pretest` hook 在測試前自動執行型別檢查（如 `"pretest": "node --run test:tsc"`）：只需要型別檢查時執行 `tsc` / `pretest`；需要測試時執行 `test`。一旦執行過 tsc/pretest，**不得隨即接著執行 `test`**（應等工作收尾之後再一次執行）；亦不得形成「（型別檢查 and/or 測試）→ 後續任務 → （型別檢查 and/or 測試）」的反覆交替循環，此即屬濫用測試行為。**例外**：後續任務若為不同階段的非同質性任務，則不受此限。

原則：測試是「驗證整體成果」的手段，而非每個微小步驟的必經程序。請累積到一定程度的工作後再統一執行測試，避免無意義地反覆觸發測試造成的資源浪費與輸出雜訊。

---

## 9. 🚫 嚴禁 `rm -rf` 等破壞性刪除操作

嚴禁在未獲授權的情況下，執行任何遞迴、強制或大量的刪除操作。

```bash
# ❌ 嚴禁（未獲授權）
rm -rf path/to/dir
rm -rf .
rm -rf /
```

```powershell
# ❌ 嚴禁（未獲授權，等效於 rm -rf）
Remove-Item -Recurse -Force path/to/dir
```

**為什麼嚴禁**：此類操作會繞過資源回收機制直接刪除；`-r`/`-Recurse` 遞迴整個子樹、`-f`/`-Force` 忽略確認與唯讀屬性，執行後難以復原，刪錯目錄也無法輕易救回。

**正確做法**：
- 任何 `rm -rf` 都必須視為高風險操作，僅在使用者於對話中**明確要求**執行該刪除時才進行，且執行前應先確認路徑。
- 不得因「清理」「重建」「重來」等模糊措辭自行決定刪除；應先確認範圍與目標，取得明確授權。
- 若確實需要移除內容，優先用安全替代（編輯工具覆寫、Move-Item 搬移、或交由使用者經資源回收桶刪除），避免直接 `rm -rf` 硬刪。
- 即使使用者已授權刪除，仍嚴禁以 `rm -rf` / `-Recurse -Force` 進行遍歷刪除；必須明確指定具體目標（單一檔案或使用者明確指名的目錄），不得對範圍外內容無差別遞迴。
- 絕不對工作區、倉庫根目錄或上層目錄執行 `rm -rf`（如 `rm -rf .`、`rm -rf /`、`rm -rf ~`），一律禁止，無例外。

## 10. 🚫 禁止編輯自動生成的產物

凡是由編譯器、產生器（codegen）、建置腳本或框架自動產出的檔案，**一律不得手動編輯**，包含但不限於：

- **同名衍生檔** — 當存在 `xxx.ts` 時，其對應的 `xxx.d.ts`、`xxx.js`、`xxx.js.map`、`xxx.d.ts.map` 均為編譯產物，不應手動編輯。
- **壓縮 / 打包檔** — `xxx.min.js`、`xxx.min.css`、`xxx.bundle.js`、`xxx.chunk.js` 等命名通常即代表編譯或打包產物。
- **建置輸出目錄** — `dist/`、`build/`、`out/`、`lib/`（視專案設定）下的所有檔案。
- **產生器輸出** — `__generated__/`、`*.generated.*`、`*.g.ts`、`autogenerated`、OpenAPI/GraphQL/Protobuf 產生的程式碼、Type Declaration 輸出、source map 等。
- **其他由腳本自動產出的檔案** — 只要是可由來源重新生成者，即屬此類。

**判斷方式**：先確認該檔案是否可由某個來源（source）經由指令重新生成。若可以 → 它就是產物，應修改來源而非產物。

**正確做法**：

- 一律回到**來源檔案**（如 `xxx.ts`）修改，再依專案既有流程重新生成產物；不得直接編輯 `.d.ts` / `.js` / `.min.js` 等產物來「繞過」來源。
- 若無法確認是否為產物、或使用者明確要求直接編輯，應先告知風險並取得授權後才進行。

> 小提醒：**建立腳本來自動生成特定檔案時，應在生成的檔案內標註該檔案為自動生成**（例如檔首加上 `// AUTO-GENERATED - DO NOT EDIT` 或等效的框架標記），以便日後辨識。

---

## 11. 🚫 測試快照檔由測試框架管理

測試的快照檔（snapshot，如 Jest/Vitest 的 `__snapshots__/*.snap`、`*.snap.new`、inline snapshot）**由測試框架管理，不應主動刪除或編輯**。

- **「更新快照」指的是**：修改與快照有關的測試程式碼，或**執行測試框架的更新機制**（如 `--updateSnapshot` / `-u` / `--update`）讓框架重新產出快照。
- **「更新快照」絕對不代表**手動編輯、覆寫或刪除快照檔；任何以手動方式改寫/刪除快照來讓測試「通過」的行為一律禁止。
- 快照的建立、更新、刪除一律交由測試框架機制處理。
- 快照失敗時，應先以唯讀方式檢視 diff、判斷是程式碼變更還是快照過期，再**告知使用者**並由其決定是否更新快照。
- 嚴禁為了讓測試通過而批量刪除快照檔、手動改寫快照內容或關閉快照比對。

---

## 12. 🚫 危險 BUG 不得擅自嘗試復現

當得知某個危險 BUG 會造成破壞性行為（例如資料汙染、覆寫或刪除檔案、外洩、未授權的網路寫入）時，**不得嘗試復現該 BUG 或案例**。

- **預設禁止復現** — 即使目的是為了除錯或撰寫測試，也不得自行執行可能觸發破壞性行為的復現步驟。
- **例外條件（兩者皆須滿足）**：
  1. 能**確保該行為是唯讀的**（不會寫入、修改、刪除任何檔案或狀態，僅產生可觀測的輸出）；
  2. 已**取得使用者明確許可**，並事先說明復現方式與潛在風險。
- 若無法確保唯讀，一律不得復現；應改以唯讀的程式碼審查、日誌分析或與使用者討論的方式進行。

## 授權判斷準則

| 使用者說法 | 是否視為明確授權 |
|---|---|
| 「安裝 X 套件」、「加入 X 依賴」 | ✅ 是 |
| 「啟動伺服器」、「跑起來」 | ✅ 是 |
| 「commit 這些變更」、「push 上去」 | ✅ 是 |
| 「修一下這個 bug」（未提及安裝） | ❌ 否，不可自行安裝 |
| 「測試一下」（未提及啟動伺服器） | ❌ 否，不可自行啟動 |
| 「更新快照」（明確指名） | ⚠️ 是，但僅限**執行框架更新機制**（`--updateSnapshot` / `-u`）或**修改與快照有關的測試程式碼**；**絕不是**手動編輯、覆寫或刪除快照檔 |
| 「修一下測試」（未提及快照） | ❌ 否，不可自行刪改快照檔 |
| 「重現這個 bug 看看」（未確認行為唯讀） | ❌ 否，不可復現 |
| 「改一下這個 `.d.ts` / `.min.js`」 | ⚠️ 視情況，應先確認是否為自動生成產物並告知風險 |
